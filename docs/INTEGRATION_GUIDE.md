# Integration Guide — Execution Layer & Control Plane

> **Purpose:** interface contract between the two products that share one Neon PostgreSQL database — who owns what, and the patterns both repos must respect. This doc intentionally does **not** hand-copy the shared schema (see below) — that has drifted from reality at least twice already and caused real bugs.

## System Overview

```
                              Neon PostgreSQL (single source of truth)
                                     │                    │
                        ┌────────────▼──────────┐ ┌────────▼─────────────────┐
                        │   EXECUTION LAYER      │ │      CONTROL PLANE       │
                        │   (this repo)          │ │      (webapp repo)       │
                        │   booking_engine on    │ │   Shop owner dashboard   │
                        │   Fly.io, read-heavy   │ │   (CRUD for all config)  │
                        └────────────┬───────────┘ └────────────┬──────────────┘
                                     │                            │
                              Twilio → OpenAI                End-user browser
                              Realtime (native SIP)           (shop owners)
```

**Execution Layer** (this repo) — handles inbound phone calls via Twilio + OpenAI Realtime API. Reads shop config, checks availability, creates/manages appointments. A single Fly.io service; see the root `README.md`.

**Control Plane** — the separate `webapp` repo. Web UI for shop owners to manage staff, services, schedules, customers, appointments, voice config, and view analytics/Inbox.

## Ownership Matrix

| Concern | Execution Layer | Control Plane |
|---------|:-:|:-:|
| **`business_app_core` schema DDL** | Adapts to it | Owns it |
| `shops`, `staff`, `services`, `staff_services`, `staff_schedules` | Read-only | Full CRUD |
| `customers` | Read + Create | Read + Update + Delete |
| `phone_contacts` | Read + Create + Upsert | Read + Delete |
| `appointments` | Read + Create + Cancel + Reschedule | Read + Update status + Delete |
| `appointment_services` | Read + Create (via appointment) | Read + Delete (via appointment) |
| **`voice_agent` schema DDL** (this repo's own) | Owns it | Reads via HTTP only, never direct SQL |
| Availability calculation | Owns the algorithm (`booking_engine/db/queries.py::get_available_slots`) | Calls the Booking Engine API |

**Key principle:** the database is the integration layer for `business_app_core` — both products connect to it directly, no API-to-API dependency required. `voice_agent` is the inverse: Control Plane reads it only through this repo's HTTP endpoints, never direct SQL.

## Shared database schema — read this before touching either

`business_app_core` is owned by the Control Plane and is **ground truth**; the Execution
Layer adapts to it, never the reverse (see `CLAUDE.md`, "Voice schema mismatch + ground-truth
rule"). Column names have silently drifted from what this doc claimed at least twice before
(`appointments.start_time/end_time` not `start_at/end_at`; `services.service_name/
duration_minutes/price_eur/is_active` not `name/duration_min/price_cents/active`;
`customers.full_name` not `first_name/last_name`; `staff` not `staff_users`) — each time
because someone hand-copied a schema snapshot into a doc and it went stale without anyone
noticing until a live call broke. **Don't repeat that here.** To get the current shape:

- inspect the live Neon branch directly (`information_schema.columns`), or
- read `booking_engine/db/queries.py`, the Execution Layer's canonical mapping onto the real
  columns, exercised by `tests/live_db/*` against real Neon-shaped data.

This repo's own `voice_agent` schema **is** authoritatively documented here — see
`booking_engine/db/sql/03_voice_agent_schema.sql` onward, applied in order (`01`/`02` are a
local-only bootstrap pair with fake data, never run against real Neon — see `scripts/migrate.sh`).

### Status lifecycle (`appointments.status`)

```
scheduled ──▶ confirmed ──▶ completed
    │             │
    ▼             ▼
cancelled      no_show
```

The Execution Layer only ever transitions `scheduled → cancelled` (cancel/reschedule —
reschedule is atomically cancel-old + create-new). The Control Plane manages every other
transition.

## Patterns & conventions

- **Multi-tenancy:** everything is scoped by `shop_id`; every query on either side must filter by it.
- **Soft deletes:** `is_active = false` on `shops`/`staff`/`services`. Never hard-delete a row with dependent appointments.
- **Timezone:** hardcoded to `Europe/Rome` in the Execution Layer today; would need a `shops.timezone` column to generalize. All `TIMESTAMPTZ` columns store UTC.
- **IDs:** UUIDs generated by Postgres (`gen_random_uuid()`), never by application code.
- **Concurrent writes to `appointments`:** the Execution Layer does SELECT-then-INSERT with overlap checking inside one transaction (see `booking_engine/db/queries.py`). Never insert without checking for a time overlap on the same `staff_id`. If the Control Plane ever writes appointments directly instead of through the Booking Engine API, it must replicate this check.

## Schema evolution rules

1. **Additive changes** (new columns with defaults, new tables/indexes) — either product can apply them, but both must be aware.
2. **Breaking changes** (renames, type changes, drops) — require a coordinated release of both products.
3. **Migration ownership** — the Control Plane owns `business_app_core` DDL; this repo owns `voice_agent` DDL (`booking_engine/db/sql/`). Whoever owns a schema applies its migrations.

## Voice Agent control-plane API

The Control Plane never touches `voice_agent` tables via direct SQL — only through this
repo's HTTP endpoints, all under `Authorization: Bearer ${CONTROL_PLANE_SECRET}`. The
authoritative, current route list is `booking_engine/api/app.py`'s `include_router` calls;
spot-check against that file rather than trusting a hand-copied table here, for the same
reason as the schema section above. As of this writing the voice-config, calls, and
analytics endpoints live under `/api/v1/voice/...` and `/api/v1/shops/{shop_id}/voice/...`
— see `docs/DEPLOY_VOICE_AGENT.md`'s smoke test for concrete, currently-passing examples.
